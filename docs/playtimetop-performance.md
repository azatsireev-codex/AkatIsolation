# PlaytimeTopCommand: оценка нагрузки и рекомендации

## Краткий вывод
Текущая реализация команды `/playtimetop` может создавать заметную нагрузку на больших серверах, потому что при каждом вызове:

1. Проходит по **всем онлайн-игрокам**.
2. Проходит по **всем офлайн-игрокам**.
3. Для каждого игрока читает статистику `PLAY_ONE_MINUTE`.
4. Полностью сортирует собранный список, хотя выводится только top-10.

Если офлайн-игроков много (сотни/тысячи), команда становится тяжёлой для главного потока.

## Что именно «дорого»

- Массовый проход по `getOfflinePlayers()`.
- Полная сортировка всех записей O(n log n) вместо выбора только 10 лучших.
- Выполнение всей логики синхронно в обработчике команды.

## Что сделать лучше

1. **Кэшировать рейтинг** (например, обновлять раз в 5–10 минут в фоне) и выдавать готовый top из памяти.
2. Для пересчёта использовать **асинхронную задачу** (с учётом ограничений Bukkit/Folia API: доступ к части API должен оставаться в безопасном контексте).
3. При пересчёте top-10 использовать структуру вроде min-heap на 10 элементов, чтобы не сортировать весь массив.
4. Увеличить/глобализировать cooldown команды (у вас уже есть 5 минут на игрока — это помогает, но не решает нагрузку в пике).
5. На очень больших серверах хранить playtime в собственной БД/таблице и строить TOP SQL-запросом.

## Практическая оценка

- **Малый сервер** (до ~100–200 офлайн-профилей): обычно терпимо.
- **Средний/крупный** (сотни и тысячи профилей): возможны лаг-спайки в момент команды.

Итог: да, опасения по нагрузке обоснованы. На небольшом онлайне — редко критично, но архитектурно команду лучше переводить на кэш + асинхронный пересчёт.
